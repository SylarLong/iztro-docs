# 多轮复核指南

完整翻译任务按下面各轮推进；专项任务聚焦指定内容，但应检查其直接依赖。各轮都以中文与对应正文为依据，不把“语法正确”“直译准确”或“程序通过”当作读者体验已经合格。

## 增量同步与范围记录

新增译文、源文同步和专项润色使用同一套复核标准，实际改动范围按任务确定。开始时记录本次语言、中文源页、目标页、变更类型和直接受影响的表格、描述及入口；长任务可在临时文件中维护清单，交付只需概括覆盖范围，不必向仓库追加过程日志。

- 中文更新时按语义单元比较变更，不仅查找新增字符串。核对被删除的条件、调整的例子、重排的表格、变化的默认值及正文已更新但摘要仍旧的情况。
- 原文更新了概念或术语时，检查该概念在目标正文、标题、表格、描述和入口的直接关联；仅改标点或个别语句时，不扩展为全站重写。
- 中文删除正文、段落、表格、页面或界面入口时，须同步删除所有其他语言（含繁体中文）的对应内容，并核对直接受影响的导航、侧栏、首页、相对链接及关联语义记录。中文新增或移动页面及锚点时，也须核对这些对应项。不要遗留指向旧位置的链接，也不要为满足结构检查恢复已删除的内容。
- 非古文章节新增古文引文时，先辨认其引文范围并补充 `classical-quote-policy.json` 的适用记录，周围现代说明照常翻译；不要因未登记引文触发中文残留检查，就把引文改译成普通正文。
- 更新记录前查明原来的核定值为何不再适用。核定译法来自中文含义、上下文和词表依据，不能把当前目标文本直接复制成“正确答案”来消除失败。
- 先确认已有未提交修改与检查基线；遇到范围外的既有错误，保留证据并在交付中说明，不擅自覆盖用户修改或宣称全量检查通过。

## 第一轮：初译后的术语、结构与表格核对

逐页对照中文，确认没有漏段、重复、错位或相反的条件。优先理解 API 行为、术语和比喻，再组织目标语言句子。

### 术语概念与已有语言示例

下表记录已有语言的概念译名示例，不是允许使用的目标语言清单。新增语言按相同中文概念建立自己的译名，再检查所有出现位置的一致性；不必先改写本表才能使用此 skill。表中译名用于正文及界面概念命名，不用于覆盖 API 中的实际字面值。专业星曜名、四化的本地化值等仍应查 `translation-terms.json`、类型定义和对应源码。未来库变更或用户明确修订后重新核定。若正文含义与库中的字面名称不同，按其所在位置区分显示用语和 API 实际值；不能用下表覆盖接口契约。

| 中文 | 英语 | 日语 | 韩语 | 越南语 |
| --- | --- | --- | --- | --- |
| 星盘 | chart | 命盤 | 명반 | lá số |
| 宫位 | palace / palaces | 宮位 | 궁 | cung |
| 星曜 | star / stars | 星曜 | 성요 | sao |
| 运限 | horoscope periods；说明中可用 time cycles | 運限 | 운한 | vận hạn |
| 主星 | major stars | 主星 | 주성 | chính tinh |
| 辅星 | auxiliary stars | 補助星 | 보조성 | phụ tinh |
| 杂曜 | miscellaneous stars | 雑曜 | 잡요 | tạp diệu |
| 神煞 | symbolic stars | 神煞 | 신살 | thần sát |

`Astrolabe`、`Horoscope` 等类型名与 `astro`、`horoscope` 等 API 名保留。无论文档译成何种语言，都不要为了统一本语言显示名而重命名代码标识符。

### 按内容类型判断，而非按外观判断

| 内容 | 处理方式 |
| --- | --- |
| 代码围栏、属性名、版本、参数与枚举示例 | 保持可执行原值；语言输入示例中的中文、韩文等字符串也可能必须保留 |
| 反引号内的普通词、比喻或算术 | 根据语义翻译；例如“外部环境”是普通表达，“加6”用 `+6`、“加减4”用 `±4` |
| 专业术语的正文显示名 | 用词表核定的本地化名称，按所在位置的括注约定处理 |
| 非古文章节中的古文引文 | 依古文记录保留繁体原文，不增添重复括注；翻译现代解释 |
| 中文显式锚点 | 保留 `{#中文原始锚点}`；翻译读者可见的标题与链接文字 |

### 表格要逐单元格读

同时检查 Markdown 表格和 HTML `<table>/<td>`。对齐源文与目标的行列、表头及单元格语义；不要只比较表格数量、形状或字面字符串。

核对名称、阴阳、五行、亮度、数值、索引、起止年龄、日期与时间边界，以及“必填/可选”“默认值/允许值”等关系。确认大限、小限、流年等概念没有互换，条件、例外和参数说明完整。

本次实际发现过的错误类型包括：

- 把星盘译成天文测量仪器，把运限译成好运或西方星座。
- 韩语把大限译成“截止期限”，把命主译成“原住民”，把四化译成“四个现代化”；把天干、地支、虚岁等换成普通词义。
- 日语把旧历说明写成含混的“太陰月”，或把安星诀写成无关联的音译；“尊贵”“富”等性质栏误用形容人的残缺形式。
- 越南语把宫位译成宫殿、把杂曜译成杂乱的“特征”、把星盘译成天文仪器。
- 英语混用 major / auxiliary / miscellaneous stars；同一组长生、博士、岁前、将前星曜，在表格、标题和说明中采用不同译名。

这些是历史语言示例，不限制新语言，也不是全库替换规则。新语言应重点排查其自身的多义词、性数格、敬语、语序或其他相关语言特性。某词在普通语境中可能完全正确；“阴”也不能仅凭字面判断为阴历或太阴星。

## 第二轮：以普通读者视角通读

先连续阅读目标语言的整段与相邻段落，再回查中文，判断读者能否理解“在讲谁、为什么、条件是什么、结论是什么”。保留原意、限制和因果，允许合并或拆分句子，避免逐字复制中文语序。

重点看代词指代、主客体、修饰关系、转折、例子与结论是否一致；特别注意条件反转、绝对化或遗漏否定。术语短语正确并不意味着整段逻辑正确。普通短语的变格、大小写和语法助词应服从目标语言语境；保持 API 字面值完整，在周围句子中组织自然语法，必要时按验证指南登记已核定的普通短语变体。

网络语言和文化比喻需要让目标语言读者理解。例如按语境说明 996/007 所指的长时间工作安排，PUA 所指的心理或情感操控；“韭菜”“创建小号”“软饭王”等不按字面套译。不要把普通游戏比喻、性格描述误当作星曜名称。

不熟悉的拼音或英语残留不能用来回避翻译。采用当前词表及 `prose-alias-review.json` 中核定的本地化表达；也不要把库的官方英文名称、品牌或实际 API 当成残留删除。

## 第三轮：标题、表格和页面描述交叉复核

重新核对所有可见标题、表头、表格标签、frontmatter `title` 和 `description`。本轮仍需读其对应正文；不能仅批量提取短文案后脱离上下文润色。

- 标题应准确概括章节内容，用词、单复数、大小写和数词形式应适合目标语言。保留源锚点、版本 Badge 和实际类型名。
- 表头区分参数、类型、是否必填、默认值、允许值和说明。语义相同的表头保持一致。
- `description` 写成简洁自然的页面摘要，避免旧 SEO 关键词堆叠、重复书名、残留包裹引号或整段正文充当摘要。
- 若中文元数据是明显复制错误，例如“配置和插件”页套用了“星曜”页摘要，应按实际正文修订目标语言摘要，并报告源文问题；不把错误继续扩散，也不借机改写范围外的中文。
- 格局页表格只保留本语言标注，不加中文括注。删除范围限于表格内的附加注解；正文、标题、古文引文以及目标语言本来的汉字术语不能一并清除。API 标记和运限后缀也不能被括号清理误删。

## 第四轮：导航、侧栏、首页和相关界面

检查 `.vitepress/locales.mjs` 和每个目标语言的 `index.md`，对照中文 `.vitepress/config.mts` 的菜单结构和页面正文。任务涉及共享界面时，再查看 `.vitepress/theme/OverflowNav.vue`、`components/donate.vue` 等实际提供文案的组件。

- 导航按入口用途命名，明确区分开发文档与知识入门。侧栏可以比标题短，但概念名称一致。例如 chart / 命盤 / 명반 / lá số，不能回退到旧的天文仪器译法。
- 首页复核名称、主标题、副标题、当前配置的入口按钮、功能卡片、AI 介绍、按钮链接与浏览器标题。重写“完整的输出”“合理的数据设计”等生硬短语时，明确它们指的是命盘数据及数据结构。
- “紫微研习社”是固定中文品牌。不要自动转换成繁体，也不使用 Zi Wei Academy、紫微斗数学習会、자미두수 학습 모임、Học viện Tử Vi 等旧译名。其他中文术语仍按各自规则处理。
- `.vitepress/locales.mjs` 从中文导航生成各语言菜单；保持对应顺序、层级和链接目标，补齐目标语言的导航词表及新导航项。不要为了润色重写导航生成逻辑。
- 站内入口指向本语言页面，外链与共享资源保持原目标，古文入口继续排除。不要把链接中文化当成文字翻译的一部分。
- 首页短按钮和品牌展示不反复附中文术语括注；也不将这个界面约定套到正文术语。
- 检查目标语言句子与相邻链接是否粘连、标题大小写是否在句中误改、短文案是否仍自然可读。文案长度明显增加时，检查桌面和窄屏菜单表现。
- 检查浏览器最终标题，避免 frontmatter 标题与站点标题叠加成两次品牌。当前首页通过 `titleTemplate: "iztro.com"` 形成“紫微研习社 | iztro.com”；先确认配置现状，避免重复添加字段。

## 最终验收：四项专项检查

在前述复核与自动验证之后，对本次目标语言和页面执行最后一遍验收；全量验收包含繁体中文，仍排除古文章节。先连续阅读目标整句与相邻上下文，再对照中文和必要的术语表或接口定义。搜索命中只能定位疑点，不能代替语义判断。

1. **专业术语与普通词义。** 核对星曜、宫位、四化、运限、格局、天干地支等概念在正文、标题、表格、描述和入口中的含义，排除按同形普通词翻译、漏掉专业限定或误换成其他概念；区分库的字面值和正文显示译名，不做无上下文的全局替换。
2. **强调词与整句衔接。** 检查反引号、粗体、斜体、链接文字及内联标签包裹的词句，连同前后助词、冠词、变格、语序和标点一起阅读。强调范围应覆盖完整语义单位，避免强调词成为孤立片段、主谓或修饰关系断裂；普通强调按语境翻译，真实标识符保留。
3. **目标语言地区的表达习惯。** 检查搭配、敬语、语体、数词、单复数、大小写、标点和文化比喻，避免中文语序、逐词拼接及不自然的音译。以该语言页面既定地区与语体为准；繁体中文也需核对用词，不只做字形转换。保留原意、条件、否定与因果。
4. **接口方法与参数。** 对照中文示例、类型定义及可访问的库源码，核对方法、属性、类型、参数名、枚举值和输入字符串，包含正文、标题、链接文字和表格中的出现位置。不得将真实标识符翻译成普通词；在标识符周围组织自然语句，解释文字照常翻译。核对大小写、调用层级及参数含义；无法确认的契约不得凭词义猜改。

发现问题时修订译文及直接受影响的核定记录，重新运行受影响检查，并重读修订后的整句。交付分别说明实际覆盖范围、修复与未确认项；自动检查通过或抽样阅读不能表述为全量人工通读通过。
